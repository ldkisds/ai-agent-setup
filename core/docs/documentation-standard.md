# 문서화 기준 (Documentation Standard)

> ai-agent-setup으로 처음 만들어진 파일입니다. 이 프로젝트에 맞게 고쳐 씁니다.

이 문서는 **무엇을 기록하고, 무엇을 기록하지 않으며, 어디에 쓰는지**의 기준입니다.
사람이 문서를 쓸 때도, 에이전트가 문서 작성을 제안할 때도 이 기준으로 판단합니다.
기준 자체를 바꾸고 싶으면 이 문서를 고치세요 — 기준이 문서 밖(머리속)에 있으면 안 됩니다.
프로젝트마다 달라지는 값(이슈 ID 형식, 릴리스 노트 형식, 주석 규칙의 예외 등)은 이 문서가 아니라 [결정 0000](decisions/0000-project-definition.md)에 둡니다.

---

## 목표

문서화는 사일로와 암묵지를 줄이기 위한 것입니다. 다만 "완전한 제거"를 목표로 삼으면 문서만 늘고 코드가 바뀔 때마다 내용이 틀려져서 오히려 못 믿게 되므로, 실제 목표는 **이해 재구축 비용을 낮추고 답변가능성(answerability)을 보존하는 것**으로 둡니다. 아는 사람이 없어도 "왜 이렇게 돼 있나"에 답할 수 있고 새 팀원(또는 에이전트)이 한 흐름을 빠르게 이해할 수 있다면, 사일로는 실질적으로 해소된 것입니다.

- **완전한 지식 이전은 불가능하다.** 누구도 시스템 전체를 머리에 유지하지 못하고, 문서가 변화 속도를 따라잡을 수도 없습니다. 가능한 것은 처음 보는 사람이 한 흐름을 끝까지 이해한 뒤 점점 넓혀 가는 것이고, 문서의 역할은 그렇게 **다시 이해하는 데 드는 비용(Re-entry cost)을 낮추는 것**입니다.
- **판정은 사람이, 도구는 증거만.** 낡은 문서 검사(Freshness check)·CI는 "어디를 볼지" 알려주는 신호이지 "문서가 틀렸다"는 판정이 아닙니다.
- 이 관점에서 **가이드**는 처음 파악할 때 들어가는 입구(Entry point — 얇게, 개수 억제), **결정 기록**은 답변가능성의 영속화(계속 쌓기 — 코드를 아무리 읽어도 복원할 수 없는 유일한 지식이 "왜"다), **낡은 문서 검사(Freshness check)**는 사람이 직접 확인할 곳을 짚어 주는 신호(Spot-check signal)입니다. 에이전트가 관여할수록 용어집·AGENTS.md·결정 기록은 에이전트가 읽는 입력으로도 쓰입니다.

참고: Goedecke, [In defense of not understanding your codebase](https://www.seangoedecke.com/in-defense-of-not-understanding-your-codebase/) · Osmani, [Own the outer loop](https://addyo.substack.com/p/own-the-outer-loop)

## 문서는 세 종류다

![문서의 세 종류 — 가이드는 지금 어떻게, how-to는 무엇을 하나, 결정 기록은 왜](images/example-doc-types.png)

| | 가이드 (`docs/*.md`) | how-to (`docs/how-to/`) | 결정 기록 (`docs/decisions/`) |
|---|---|---|---|
| 답하는 질문 | 코드가 **지금 어떻게** 동작하는가, 사람이 지킬 규약은 무엇인가 | 목표를 이루려면 **무엇을 하나** | **왜 그렇게** 만들었는가 |
| 시간이 지나면 | **코드가 바뀌면 틀려진다** → 같이 고쳐야 함 | **실행 방법이 바뀔 때만 틀려진다** | **틀려지지 않는다** → 그때 내린 결정의 기록이라 수정하지 않음 |
| 운영 원칙 | 개수를 늘리지 않는다 (유지비용이 높으므로) | 두 번 설명한 것만 적는다 ([아래](#how-to는-왜-따로인가)) | 부담 없이 쌓는다 (append-only) |

핵심 규칙: **"왜"는 가이드에 길게 섞지 말고 결정 기록으로 분리**합니다. 가이드에는 한 줄 요약 + 결정 기록 링크만 남깁니다. 가이드가 짧을수록 고칠 곳이 적어 오래 맞는 상태로 남습니다.

- **예외 — 결정 0000(프로젝트 정의)**은 프로젝트의 현재 정의·설정값을 담으므로, 바뀌면 그 자리에서 갱신합니다.

## 기록한다

판단 기준은 하나입니다 — **"코드를 아무리 읽어도 알 수 없는가?"** 그렇다면 기록 대상입니다.

- **설계 결정과 그 이유, 버린 대안** — 예: "캐시를 메모리가 아니라 파일에 둔 이유"
- **코드 밖에 근거가 있는 제약** — 고객사 요구사항, 외부 데이터 계약, DB 컬럼의 불변/가변 규칙 등
- **실패한 시도** — 같은 길을 다시 가지 않도록. "해봤는데 안 됐다"는 가장 비싼 지식입니다
- **두 번 이상 설명하게 된 것** — 동료나 에이전트에게 같은 걸 두 번 설명했다면, 그건 문서 공백입니다
- **코드에 드러나지 않는 도메인 규칙** — 용어, 현실 세계의 물리적/설계적 이유

## 기록하지 않는다

- **코드를 읽으면 알 수 있는 것** — 함수가 무엇을 하는지, 클래스 구조가 어떤지. 에이전트에게 코드를 읽히면 되는 내용은 문서로 중복하지 않습니다
- **상수에서 파생되는 수치를 여러 곳에 쓰는 것** — 개수, 구간 수, 임계값처럼 상수 하나에서 나오는 숫자는 **그 상수의 값이 함께 적힌 한 곳**에만 씁니다. 나머지는 숫자 대신 구조로 씁니다 — "최대 3회 재시도"가 아니라 "`MAX_RETRY`만큼 재시도". 판정은 **"이 상수가 바뀌면 고쳐야 할 문장이 몇 개인가"**입니다. 2개 이상이면 잘못 쓴 것입니다. 숫자는 독자에게 요약으로 보이지만 유지하는 쪽에는 **갱신해야 할 사본**입니다
- **일회성 정보** — 특정 이슈에서만 의미 있는 디버깅 **경위**(이 버그를 어떻게 쫓았는지)는 이슈에만 남깁니다. 단, 그 과정에서 쓴 **재현 가능한 절차**(로그를 어디서 보나, 특정 케이스만 어떻게 돌리나)는 다음 사람에게도 필요하므로 [how-to/](how-to/README.md)로 갑니다 — 가르는 축은 "이 이슈에만 해당하는가"입니다
- **가이드 안의 이력·실측·버린 대안** — 가이드에는 현재 사실과 한 줄 이유만 둡니다. "~로 변경됨" 식의 이력은 릴리스 노트가, 배경과 버린 대안은 결정 기록이, 실측 수치와 조사 경위는 이슈가 맡고, 가이드는 그곳을 링크합니다
- **외부에 이미 잘 정리된 일반 지식** — 널리 알려진 알고리즘·라이브러리의 일반 이론은 링크로 대체합니다

### how-to는 왜 따로인가

가이드(`docs/*.md`)는 **시스템이 스스로 하는 일**을 설명하고, `how-to/`는 **사람이 하는 일**을 적습니다. 둘을 나누는 이유는 내용이 틀려지는 시점이 다르기 때문입니다 — 알고리즘 설명은 코드가 바뀌면 바로 틀려지지만, "어떻게 돌리나"는 실행 방법이 바뀔 때만 틀려집니다.

그래서 **`how-to/`는 "가이드 개수를 늘리지 않는다" 원칙의 적용 대상이 아닙니다.** 쓸 계기는 **"두 번 이상 설명하게 된 것"**입니다. 한 문서를 처음부터 완성하려 하지 말고, **실제로 두 번 설명한 것만** append 하세요 — 빈 절을 미리 만들면 그 문서 전체가 못 믿을 문서가 됩니다.

## 코드 주석

### 주석의 목적

주석은 **코드만 읽어서는 알 수 없는 것**을 코드 옆에 남기는 문서입니다. 다만 코드를 고칠 때 **함께 고치지 않으면 가장 먼저 틀려지고, 동시에 가장 자주 읽힙니다.** 그래서 아래 기준으로 남길 것과 남기지 않을 것을 가립니다. 이 절의 규칙은 언어와 상관없이 같고, 주석 기호(`#` · `//` · `--` 등)와 문서 주석 문법만 언어에 맞춥니다.

**남기는 주석**

| 주석의 내용 | 처리 |
|---|---|
| **의도와 맥락** — 코드만으로 드러나지 않는 비즈니스 규칙의 배경, 알고리즘을 고른 이유, 트레이드오프(장단점) | **한두 줄로 남김.** 배경·버린 대안처럼 옮길 내용이 있으면 결정 기록 + 포인터 ([아래](#결정-기록-포인터)) |
| **경고와 주의사항** — 사소해 보이지만 지우거나 바꾸면 치명적인 것(외부 시스템·다른 팀이 쓰는 이름·필드, 문자열·설정으로만 연결돼 검색에 안 걸리는 코드), 예상하지 못한 부작용(side effect), 반드시 지켜야 하는 실행 순서, 단위·경계 포함/배제·불변식 | **한 줄로 압축해 남김.** 배경이 있으면 결정 기록 + 포인터. 테스트로 막을 수 있으면 테스트가 먼저 |
| **함수 계약** — 무엇을 받고 무엇을 돌려주는가 | **함수 설명**으로 씀 ([아래](#함수-설명-google-스타일)). 타입은 주석보다 타입 표기(Python Type Hint, TypeScript 타입 등)로 먼저 드러냄 |
| **미완료 작업** — 당장 구현하지 못한 기능, 고쳐야 할 기술 부채 | **`TODO(<이슈ID>): …`**(할 일) · **`FIXME(<이슈ID>): …`**(알려진 문제). 이슈 ID가 없는 TODO는 아무도 추적하지 않아 그대로 남음 |
| **법적·저작권 정보** — 라이선스 고지, 저작권 표기 | **그대로 남김** |

**남기지 않는 주석**

| 주석의 내용 | 처리 |
|---|---|
| **코드를 그대로 옮긴 설명** — `i = i + 1  # i에 1을 더한다` | **지움** |
| **주석 처리된 코드** — 쓰지 않는 코드 | **지움** — 필요하면 버전 관리(git) 이력에서 찾음 |
| **변경 이력** — 파일 상단의 수정 날짜·작성자·수정 내용 | **지움** — 버전 관리(git)가 담당 |
| **모호한 표현** — 무엇을 가리키는지 모를 대명사("이것", "it"), 틀린 내용 | **분명하게 고치거나 지움** — 틀린 주석은 없는 것보다 해로움 |
| **나쁜 코드를 가리는 주석** — 복잡한 코드를 주석으로 설명 | **리팩터링이 먼저** — 이름을 바꾸거나 함수를 나눔 |
| **긴 주석** — 8줄을 넘는 연속 주석 (태그·기호만 있는 줄을 뺀 산문 줄, 블록 전체 기준) | **결정 기록으로 옮기고 포인터만 남김** — 옮길 내용이 있다는 신호 |

> 목표는 **"긴 주석 0"이지 "주석 0"이 아닙니다.**

### 결정 기록 포인터

**코드에 둘까, 결정 기록으로 옮길까** — 가르는 축은 **"사소한가"가 아니라 "옮길 내용이 있는가"**입니다. 판정 도구는 [decisions/TEMPLATE.md](decisions/TEMPLATE.md)의 `## 배경`·`## 버린 대안` 절입니다 — **채울 수 있으면 결정 기록으로 옮기고, 못 채우면 코드에 한 줄로 남깁니다.**

중요도가 높아도 **자족적인 단일 사실이면 코드에 남깁니다.** 예를 들어 "이 비교 순서가 바뀌면 결과가 조용히 틀어진다"는 주석은 중요하지만, 배경도 버린 대안도 없어 결정 기록 1장 분량이 되지 않습니다. 이런 것을 억지로 옮기면 결정 기록이 한 줄짜리로 불어나고, 정작 코드에서는 그 사실이 사라집니다.

결정 기록으로 옮겼다면, 원래 주석 자리에 **포인터 한 줄**만 남깁니다. 포인터는 경로가 아니라 **`(결정 NNNN)`** 형식입니다 — 처음 보는 사람도 결정 기록을 가리킨다는 것을 알 수 있고, 결정 기록 파일명이 바뀌어도 깨지지 않습니다.

```text
시도 구간이 공유 상태를 전혀 바꾸지 않는다는 전제 위에 서 있다 (결정 0042).
```

- 괄호 안에는 **`결정` + 번호만** 넣습니다. 복수는 `(결정 0037, 0039)`처럼 나열하고, 경로·파일명·`.md`는 붙이지 않습니다.
- 참조는 **주석 블록의 맨 끝에 한 번만** 답니다. 여러 문장이 서로 다른 기록에 걸리면 번호를 모아 끝에 답니다.
- 이 형식은 **코드 주석 전용**입니다. 문서끼리는 클릭되는 풀 경로 링크를 씁니다.
- 번호에서 문서로는 `docs/decisions/0042*`로, 코드에서 관련 기록으로는 각 기록의 `## 관련` 절 코드 경로로 서로 닿습니다.

옮기고 포인터를 남기지 않으면 지식이 코드에서 완전히 사라져, 나중에 리팩터링하는 사람이 "이건 왜 이렇지?"에 답할 길이 없어집니다.

### 함수 설명 (Google 스타일)

함수 설명은 **Google 스타일**로 씁니다. 구성은 언어와 상관없이 같습니다.

1. **요약 한 줄** — 함수가 무엇을 하는지 (필요하면 빈 줄 뒤에 상세 설명)
2. **인자** — 각 인자의 이름과 의미
3. **반환값** — 무엇을 돌려주는지
4. **예외** — 어떤 경우에 무엇을 던지는지

해당 없는 항목은 생략합니다. 표기는 그 언어의 Google 스타일 가이드를 따릅니다 — Python은 docstring의 `Args:` · `Returns:` · `Raises:`, JavaScript·TypeScript는 JSDoc의 `@param` · `@return` · `@throws`, Java는 Javadoc 태그입니다.

```python
# 예: Python
def load_orders(path: str, since: date | None = None) -> list[Order]:
    """주문 파일을 읽어 주문 목록을 반환한다.

    Args:
        path: 주문 CSV 파일 경로.
        since: 이 날짜 이후 주문만 읽는다. None이면 전체를 읽는다.

    Returns:
        읽은 주문 목록. 파일이 비어 있으면 빈 목록.

    Raises:
        FileNotFoundError: path에 파일이 없을 때.
    """
```

**언제 쓰나** — Google 기준을 따릅니다. 아래 중 하나라도 해당하면 **반드시** 씁니다.

- 외부(다른 모듈·사용자)에 공개된 함수
- 길이가 긴 함수
- 로직이 자명하지 않은 함수

셋 다 아닌 함수 — 내부용이고, 짧고, 이름만으로 하는 일이 분명한 함수 — 는 생략할 수 있습니다. 그런 함수의 요약은 코드에서 바로 읽히고 에이전트도 즉시 재구성할 수 있어, 갱신 비용만 남기 때문입니다.

**담지 않는 것** — 함수 설명은 "무엇을 받고 무엇을 돌려주나"(계약)만 담습니다. 구현 단계 설명은 쓰지 않고, 배경·버린 대안은 결정 기록으로 옮겨 요약 끝에 포인터를 답니다. 8줄 제한은 요약·상세 설명 산문에만 적용하고 인자·반환값·예외 항목은 세지 않습니다.

### 프로젝트마다 정하는 것

주석 규칙의 예외 범위(예: 검산용 코드), 소스를 외부에 전달할 때의 규칙(예: 문서 존재를 감추려고 포인터를 `(0042)`처럼 번호만 쓰기, 주석 금지어·검사 훅)은 [결정 0000](decisions/0000-project-definition.md)의 리포 고유 규칙에 둡니다.

## 문서를 코드와 맞게 유지하기 (Freshness)

- 가이드가 설명하는 코드를 바꿨다면, **가이드 갱신도 같은 브랜치(이슈)의 작업**입니다. 당장 못 고치면 해당 문단에 `> ⚠️ TODO(<이슈ID>): 코드와 어긋남` 표시라도 남깁니다.
- 결정 기록은 수정하지 않습니다(결정 0000 제외). 결정이 뒤집히면 **새 기록을 쓰고 이전 기록을 "대체됨"으로 표시**합니다.

### 가이드 frontmatter

모든 가이드는 맨 위에 frontmatter를 갖습니다. 의미는 하나 — **"`last-verified` 이후 `anchors`가 바뀌었다면 이 문서를 의심하라."**

```yaml
---
anchors:                          # 이 문서가 설명하는 코드 경로 (디렉터리 단위 우선)
  - src/module-a/
  - src/module-b/
last-verified: 2026-01-01         # 이 날짜 시점의 코드와 일치함을 확인함
---
```

- `last-verified`는 **날짜**를 씁니다. 커밋 해시는 squash merge 시 기본 브랜치에서 사라질 수 있어 쓰지 않습니다.
- 문서를 검토·갱신할 때마다 `last-verified`를 그날 날짜로 올립니다.
- 앵커는 파일명 변경에 강한 **디렉터리 단위를 우선**하고, 문서당 3~7개를 유지합니다.
- 개념 수준 문서는 `anchors: []`로 두고 주기 리뷰로만 점검합니다.

**낡은 문서 검사**: 가이드마다 `last-verified` 이후 `anchors`의 코드에 커밋이 있었는지 확인합니다.

```text
git log --since=<last-verified> --oneline -- <anchors>
```

결과가 나온 가이드는 사람이 읽어 보고, 내용을 고치거나 그대로 맞으면 `last-verified`만 그날 날짜로 올립니다. 결과가 나왔다고 문서가 틀린 것은 아닙니다. 확인할 곳이라는 신호입니다.
