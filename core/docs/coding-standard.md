# 코드 작성 기준 (Coding Standard)

> * 이 문서는 **코드를 읽기 쉽게 쓰는 기준**입니다. 사람이 코드를 쓸 때도, 에이전트가 코드를 작성·수정·리팩터링·리뷰할 때도 이 기준으로 판단합니다.
팀의 코드 스타일이 따로 있으면 이 문서를 그 내용으로 바꾸거나 고쳐 쓰세요 — 기준이 문서 밖(머리속)에 있으면 에이전트가 따를 수 없습니다.
>* 기본 내용은 『읽기 좋은 코드가 좋은 코드다 (The Art of Readable Code)』의 [서평 정리](https://apeltop.github.io/docs/book-review/the-art-of-readable-code/)를 바탕으로 했고, 블로그의 예시 중 버그가 있던 부분은 바로잡아 실었습니다.

## 적용 방법

- **적용 시점:** 코드를 새로 쓰거나, 수정하거나, 리팩터링하거나, 리뷰할 때 항상 적용합니다.
- **우선순위:** 프로젝트의 기존 컨벤션, 린터·포매터 설정, `AGENTS.md`, [문서화 기준](documentation-standard.md)과 다르면 **그쪽을 따릅니다.** 이 문서는 그 규칙들이 정하지 않은 부분을 채웁니다.
- **범위:** 요청받은 변경 범위 안에서만 적용합니다. 이 기준을 이유로 관련 없는 코드를 고치지 않고, 고칠 만한 곳을 발견하면 따로 알립니다.
- **마무리:** 작업을 끝내기 전에 맨 아래 [체크리스트](#체크리스트)로 변경한 코드를 확인합니다.

## 1. 이름에 정보 담기

### 1.1 구체적인 단어를 씁니다
`get`, `data`, `stop`처럼 뜻이 넓은 단어를 피하고 동작을 정확히 드러냅니다.

| ❌ | ✅ | 이유 |
|---|---|---|
| `getImages()` | `fetchImages()` | 네트워크에서 가져온다는 점이 드러남 |
| `stop()` | `pause()` / `resume()` | 다시 시작할 수 있는 동작이라면 |

### 1.2 단위를 이름에 넣습니다
시간, 크기 같은 측정값에는 단위를 붙입니다.

```js
function timeout(delay) {}          // ❌ ms인가 s인가?
function timeout(delayMs) {}        // ✅
function timeout(delaySecs) {}      // ✅

function fileSizeLimitCheck(size)   // ❌
function fileSizeLimitCheck(sizeMb) // ✅
```

### 1.3 중요한 속성을 이름에 넣습니다
보안, 인코딩, 상태처럼 잘못 쓰면 위험한 속성은 이름에 드러냅니다.

```js
const password = ..;           // ❌
const plainTextPassword = ..;  // ✅

const data = ..;               // ❌
const dataUrlEnc = ..;         // ✅ URL 인코딩된 값
```

## 2. 오해할 수 없는 이름

### 2.1 뜻이 두 가지인 동사를 피합니다
- `filter()`는 남기는 건지 빼는 건지 모호합니다. → 고르면 `select()`, 빼면 `exclude()`.

### 2.2 경계를 포함하는지 이름으로 나타냅니다

| 의미 | 이름 |
|---|---|
| 양 끝을 포함하는 한계값 | `min`, `max` (예: `MAX_ITEMS`) |
| 양 끝을 포함하는 범위 | `first`, `last` |
| 시작은 포함하고 끝은 제외하는 범위 | `begin`, `end` |

### 2.3 사용자가 기대하는 대로 짓습니다
- `get*`은 가벼운 접근자로 기대됩니다. 계산 비용이 크면 `compute*`, `calculate*` 등을 씁니다.
- ❌ `getMean()` (전체를 순회해 계산) → ✅ `computeMean()`

## 3. 주석 쓰기

주석을 남길지, 어디에 쓸지(코드 주석·결정 기록), `TODO(<이슈ID>)`·`FIXME(<이슈ID>)` 형식은 문서화 기준의 [코드 주석](documentation-standard.md#코드-주석)을 따릅니다.

남기기로 한 주석에 코너 케이스가 있으면 **입출력 예시**로 보여 줍니다.

```java
// 'src'의 앞뒤에서 'chars'에 속한 문자를 제거한다.
// 예: strip("abba/a/ba", "ab") → "/a/"
String strip(String src, String chars) { ... }
```

```ts
/** 예: 2022.08.20. */
export function momentL(value: string | Date) {
  return moment(value).locale('ko').format('L');
}
/** 예: 2022년 8월 20일 */
export function momentLL(value: string | Date) {
  return moment(value).locale('ko').format('LL');
}
```

---

## 4. 함수 나누기

- 상관없는 하위 문제를 함수로 뺄 때 **너무 잘게 나누지 않습니다.** 함수가 너무 많으면 실행 흐름을 따라 여기저기 옮겨 다녀야 해서 오히려 읽기 어렵습니다.

---

## 5. 코드 분량 줄이기

- **필요하지 않은 기능은 만들지 않습니다.** 개발자는 필요한 기능의 양을 크게 잡고 구현 비용은 작게 잡는 경향이 있습니다. 지나친 확장성은 나중에 고치는 비용을 키웁니다.
- **표준 라이브러리, 프레임워크, 기존 유틸을 먼저 찾습니다.** 직접 만들기 전에 이미 있는 API나 옵션으로 해결되는지 확인합니다. (예: 이미지 슬라이더를 직접 구현하지 않고 `FlatList`의 `pagingEnabled` 옵션 사용)
- 새로 쓴 코드는 모두 테스트하고, 문서화하고, 유지보수해야 합니다. **가장 읽기 좋은 코드는 아예 없는 코드입니다.**

---

## 6. 테스트

- **가장 단순한 입력으로 코드를 충분히 검증합니다.** 많은 데이터보다 꼭 필요한 몇 개가 낫습니다.

---

## 체크리스트

코드를 내놓기 전에 아래를 확인합니다.

**이름**
- [ ] 이름이 구체적인가? (`get`, `data`, `tmp`, `filter` 같은 모호한 단어가 없는가)
- [ ] 측정값에 단위가 있는가? (`Ms`, `Secs`, `Mb` 등)
- [ ] 위험한 속성(평문, 인코딩 여부, 미검증 등)이 이름에 드러나는가?
- [ ] 범위 이름이 `min/max`, `first/last`, `begin/end` 규칙을 따르는가?
- [ ] 무거운 연산에 `get`을 쓰지 않았는가?

**주석** (남길지와 형식은 [문서화 기준](documentation-standard.md#코드-주석))
- [ ] 코드를 그대로 되풀이하거나, 이름을 고치면 필요 없어지는 주석이 없는가?
- [ ] 코드만으로 알 수 없는 의도와 주의사항을 짧게 남겼는가?
- [ ] 코너 케이스가 있으면 입출력 예시로 보여 주는가?
- [ ] `TODO`·`FIXME`에 이슈 ID를 붙였는가? (`TODO(<이슈ID>): …`)

**분량과 테스트**
- [ ] 요청받지 않은 기능이나 과한 확장성을 넣지 않았는가?
- [ ] 표준 라이브러리나 기존 유틸로 대신할 수 있는 코드를 직접 만들지 않았는가?
- [ ] 함수를 너무 잘게 나누지 않았는가?
- [ ] 테스트 입력이 꼭 필요한 몇 개로 단순한가?

> **판단이 갈릴 때:** "이 코드를 처음 보는 사람이 가장 빨리 이해할 수 있는 형태는 무엇인가?"를 기준으로 고릅니다.
