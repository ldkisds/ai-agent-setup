# 릴리스 노트 작성

형식은 같은 폴더의 [template.md](template.md)를 따른다. 프로젝트마다 다른 값은 결정 0000에서 읽는다. 제목·버전 형식 등은 "릴리스 노트" 설정에, "구성 요소"는 설정값 표에 있다.

## 1. 비교할 두 태그 정하기

사용자는 태그를 0~2개 준다.

| 받은 태그 | 이전 태그 | 나중 태그 |
|---|---|---|
| 없음 | 가장 최근 태그 바로 전 태그 | 가장 최근 태그 |
| 1개 | 받은 태그 | 가장 최근 태그 |
| 2개 | 둘 중 이전 것 | 둘 중 나중 것 |

1. 원격 저장소가 없으면(`git remote` 결과가 비어 있음) "원격 저장소가 없습니다."라고만 알리고 멈춘다.
2. `git fetch --tags`로 원격 태그를 받는다. 네트워크 제한 등으로 실패하면 로컬 태그로 계속 진행하고, 원격 태그가 빠졌을 수 있다고 알린다.
3. 태그가 하나도 없으면(`git tag --list` 결과가 비어 있음) "태그가 없습니다."라고만 알리고 멈춘다.
4. 태그를 3개 이상 받았으면 멈추고 다시 묻는다.
5. 받은 태그가 실제로 있는지 확인한다: `git rev-parse --verify --quiet "refs/tags/<태그>"`. 없으면 `git tag --list`에서 비슷한 이름을 찾아 제안하고 멈춘다.
6. 받지 못한 태그는 자동으로 고르고, 무엇을 골랐는지 알린다.
   - 가장 최근 태그: 기본 브랜치(결정 0000)에 merge된 가장 최근 태그. `git describe --tags --abbrev=0 <기본 브랜치>`. 실패하면(기본 브랜치에 태그가 없음) 알리고 멈춘다.
   - 그 바로 전 태그: `git describe --tags --abbrev=0 <가장 최근 태그>^`
   - 바로 전 태그가 없으면(태그가 하나뿐) 첫 커밋부터 비교할지 묻는다. 그렇게 하면 이전 태그 자리에 "첫 커밋"이라고 쓰고, 2단계 명령의 `<이전>..<나중>` 대신 `git log`에는 `<나중>`만, `git diff`에는 이전 쪽에 빈 트리 `4b825dc642cb6eb9a060e54bf8d69288fbee4904`를 쓴다.
7. 두 태그의 순서를 정한다. 받은 순서와 상관없이 git 이력을 따른다.
   - `git merge-base --is-ancestor <A> <B>`가 성공하면 A가 이전 태그, B가 나중 태그다.
   - 같은 태그면 멈춘다.
   - 어느 쪽도 다른 쪽의 조상이 아니면, 서로 다른 브랜치의 태그라고 알리고 계속할지 묻는다. 계속하면 태그가 가리키는 커밋 날짜가 빠른 쪽을 이전 태그로 한다.

## 2. 변경 모으기

- 커밋 목록: `git log --no-merges --format="%h %s" <이전>..<나중>`
- PR 단위 목록: `git log --merges --format="%h %s" <이전>..<나중>`
- 파일 목록: `git diff --name-status --no-renames <이전>..<나중>`. `A`는 추가, `M`은 수정, `D`는 삭제다. 이름이 바뀐 파일은 삭제와 추가로 나온다.
- 쿼리 파일: 파일 목록 중 결정 0000의 "DB 쿼리 파일 위치"에 있는 추가·수정 파일
- 커밋 메시지만으로 무엇이 바뀌었는지 알기 어려우면 그 커밋의 diff를 본다.

## 3. Release Note 항목 정리

- **구성 요소별로 묶는다.** 구성 요소 이름과 경로의 대응은 결정 0000의 "구성 요소"를 따른다.
  - 대응이 없으면 바뀐 파일의 최상위 폴더로 묶어 초안을 만들고, 구성 요소 이름을 사용자에게 확인받는다. 확인한 대응은 결정 0000에 추가할지 묻는다.
- **넣는 변경**: FEAT, FIX, 사용자에게 영향이 있는 REFACTOR·BUILD (TYPE은 `AGENTS.md`의 "커밋")
- **빼는 변경**: TEST, DOCS, CHORE. 이 파일들은 업데이트 파일 리스트에는 그대로 나온다.
- 한 항목은 사용자 관점에서 무엇이 바뀌었는지 한 줄로 쓴다. 예: "EndPoint와 RackSegment가 같은 section에 있을 경우 신규 로직 적용"
  - 커밋 메시지를 그대로 붙이지 않고, 비슷한 커밋은 하나로 합친다.
- TYPE이 없는 커밋은 메시지와 diff를 보고 판단한다. 확신이 없으면 따로 모아 사용자에게 묻는다.
- 호환성이 깨지는 변경(입출력 형식, 설정 이름 등)이나 배포 때 할 일은 "참고사항"에 적는다.

## 4. 작성

[template.md](template.md)의 섹션 순서와 이름을 그대로 쓴다. **비어 있는 섹션도 지우지 않는다.**

| 부분 | 채우는 법 |
|---|---|
| 제목 | 결정 0000의 "제목 형식". 날짜는 나중 태그가 가리키는 커밋의 날짜(`git log -1 --format=%as <나중 태그>`)다. 차수(N차)는 `release-note/`에 있는 이전 파일의 제목에서 가장 큰 차수를 찾아 그다음 번호로 하고, 이전 파일이 없으면 사용자에게 묻는다 |
| 버전 | 결정 0000의 "버전 형식" 설명과 나중 태그 |
| 배포용 소스 | 에이전트가 첨부할 수 없으므로 자리만 남긴다 |
| Release Note | 3단계에서 정리한 구성 요소별 항목 |
| 업데이트 쿼리 리스트 | 쿼리 파일의 경로와 내용(코드 블록). 없으면 "없음" |
| Added / Modified / Deleted Files | 2단계 파일 목록을 경로순으로 적는다. 비어 있으면 "없음" |
| Delivery File Tree | 추가·수정 파일 중 결정 0000의 "배포에서 뺄 경로"를 뺀 파일로 트리를 그린다. 트리의 파일 수가 목록의 파일 수와 같은지 확인한다 |
| 참고사항 | 3단계에서 모은 주의할 점. 없으면 비운다 |

커밋, diff, 파일 목록에서 확인한 내용만 쓴다. 추측해서 채우지 않는다.

## 5. 저장

프로젝트 루트의 `release-note/` 폴더에 `release-note-<나중 태그>.md`로 저장한다.

```
<프로젝트 루트>/
└─ release-note/
   ├─ release-note-2026.07.03.md
   └─ release-note-<나중 태그>.md
```

- `release-note/` 폴더가 없으면 만든다.
- 태그에 `/`가 들어 있으면 파일 이름에서는 `-`로 바꾼다. 예: `release/1.2` → `release-note-release-1.2.md`
- 같은 이름의 파일이 이미 있으면 덮어쓰지 않고, 덮어쓸지 사용자에게 묻는다.
- 저장한 뒤에는 파일 경로와 Release Note 항목 요약을 알린다.
- 커밋, 태그 만들기, push, 다른 곳(Confluence, GitHub Releases 등)에 올리기는 하지 않는다. 사용자가 요청하면 그때 따로 묻고 한다.
