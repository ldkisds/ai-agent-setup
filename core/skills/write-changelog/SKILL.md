# 프로젝트 변경 이력 작성

이 프로젝트에서 버전마다 무엇이 바뀌었는지를 프로젝트 루트의 `CHANGELOG.md`에 쌓아 간다. 새 버전은 항상 **맨 위**에 추가해서 최신 내용이 먼저 보이게 한다.

- 처음 실행하면 `CHANGELOG.md`를 만들고 첫 항목을 채운다. 그다음부터는 실행할 때마다 맨 위에 한 항목씩 추가한다.
- `.ai-agent-setup/CHANGELOG.md`는 ai-agent-setup 자체의 이력이므로 읽지도 고치지도 않는다.

## 형식

```
version: <버전>
summary: <한 줄 요약> [<이슈ID>]
items:
    <변경 종류>:
        - [<구성 요소>]
            - <바뀐 점> — <덧붙일 설명>
```

예:

```
version: v0.3.3
summary: Keeping Existing PSN 목록에 패턴 태그 표기 [EPAR-850]
items:
    updated:
        - [GraphUI]
            - 패턴으로 통째 그려진 PSN을 `이름(패턴 태그)`로 표기 — 프론트엔드 번들 교체
            - 기대 프론트 버전 v0.17.22

version: v0.3.2
summary: 데이터 갱신 알림 시 그래프 갱신 [EPAR-851]
items:
    fixed:
        - [GraphUI]
            - 데이터 갱신 알림을 받아도 그래프가 그대로이던 문제 수정 — 알림 시 전처리 재실행
```

- 들여쓰기는 공백 4칸씩이다.
- 변경 종류는 `added`(추가), `updated`(변경), `fixed`(수정), `removed`(삭제) 순서로 쓰고, 해당하는 것이 없는 종류는 뺀다.

## 1. 버전 정하기

- 사용자가 버전을 함께 줬으면(예: `/write-changelog v0.3.3`) 그대로 쓴다.
- 주지 않았으면 `CHANGELOG.md` 맨 위 항목의 버전과 최근 태그(`git tag --sort=-creatordate`)를 보여 주고, 이번 버전을 묻는다.
- 같은 버전의 항목이 이미 있으면 덮어쓰지 않고, 그 항목을 고칠지 묻는다.

## 2. 변경 모으기

어디서부터 모을지는 아래 순서로 정하고, 무엇을 기준으로 했는지 알린다.

1. 사용자가 범위를 줬으면 그대로 쓴다.
2. `CHANGELOG.md` 맨 위 항목의 버전과 같은 이름의 태그가 있으면: `<그 태그>..HEAD`
3. 없으면 `CHANGELOG.md`를 마지막으로 고친 커밋 이후: `git log -1 --format=%h -- CHANGELOG.md`로 찾은 커밋에서 `HEAD`까지
4. `CHANGELOG.md`가 없거나 위 방법으로 정할 수 없으면 사용자에게 묻는다.

모을 것:

- 커밋: `git log --no-merges --format="%h %s" <범위>`
- PR 단위: `git log --merges --format="%h %s" <범위>`
- 이슈 ID는 커밋 메시지 맨 앞(`<이슈ID> TYPE: …`), merge 메시지, 브랜치 이름에서 찾는다. 이슈 ID 형식은 결정 0000을 본다.
- 아직 커밋하지 않은 변경: `git status`, `git diff HEAD`. 변경 이력은 보통 버전을 올리기 직전에 쓰므로 함께 포함한다.
- 커밋 메시지만으로 무엇이 바뀌었는지 알기 어려우면 diff를 본다.

프로젝트가 git 저장소가 아니면 이번 버전에서 바뀐 점을 사용자에게 묻는다.

## 3. 분류

| 변경 종류 | 넣는 변경 |
|---|---|
| `added` | 새 기능 (FEAT 중 새로 생긴 것) |
| `updated` | 기존 기능의 동작 변경 (FEAT 중 바뀐 것, 사용자에게 영향이 있는 REFACTOR·BUILD) |
| `fixed` | 버그 수정 (FIX) |
| `removed` | 기능 삭제 |

- TEST, DOCS, CHORE처럼 사용자에게 보이지 않는 변경은 넣지 않는다.
- 커밋 TYPE은 `AGENTS.md`의 "커밋"을 따른다. TYPE이 없거나 애매하면 diff를 보고 판단하고, 확신이 없으면 사용자에게 묻는다.
- **구성 요소**별로 묶는다. 구성 요소 이름과 경로의 대응은 결정 0000의 "구성 요소"를 따른다. 대응이 없으면 바뀐 파일의 최상위 폴더로 묶어 초안을 만들고, 이름을 사용자에게 확인받는다.

## 4. 작성

- **summary**: 이번 버전의 핵심 변경을 한 줄로 쓰고, 관련 이슈 ID를 대괄호로 붙인다. 여러 개면 `[A-1, A-2]`로 쓴다. 이슈 ID를 찾지 못하면 사용자에게 묻고, 없다고 하면 뺀다.
- **항목**: 사용자 관점에서 무엇이 바뀌었는지 한 줄로 쓴다. 이유나 방법은 `—` 뒤에 짧게 붙인다. 함께 맞춰야 할 버전이나 설정이 있으면 항목으로 따로 적는다. 예: "기대 프론트 버전 v0.17.22"
- 커밋 메시지를 그대로 붙이지 않고, 비슷한 커밋은 하나로 합친다.
- 커밋과 diff에서 확인한 내용만 쓴다. 추측해서 채우지 않는다.

## 5. 저장

- 저장 위치는 프로젝트 루트의 `CHANGELOG.md`다.
- **새 항목은 맨 위 항목 바로 앞에 넣고, 빈 줄 하나로 구분한다.** 파일 맨 앞에 제목이나 설명이 있으면 그 아래, 첫 `version:` 줄 앞에 넣는다. 항목들이 코드 블록(```` ``` ````) 안에 있으면 코드 블록 안의 맨 위에 넣는다.
- `CHANGELOG.md`가 없으면 새로 만든다. 맨 위에 `# 변경 이력 (Changelog)` 제목을 두고, 항목은 코드 블록 안에 쓴다. 마크다운으로 볼 때 들여쓰기가 무너지지 않게 하기 위해서다.
- 기존 파일의 줄바꿈 형식(CRLF/LF)을 유지한다.
- 저장한 뒤 추가한 항목을 보여 준다. 커밋은 하지 않는다. 사용자가 요청하면 그때 따로 묻고 한다.
